# NailDIY 产品需求文档（PRD）

> 项目：基于 Spring Boot 的 DIY 穿戴甲定制平台
> 版本：v1.0　｜　更新：2026-10-13
> 配套文档：《项目功能技术详解》《答辩应对手册》《项目使用文档》《数据库与部署指南》

## 一、研究背景与意义

### 1.1 行业背景

美甲已从"到店服务"演变为高频日常消费，其中**穿戴甲**是增长最快的细分品类。相比传统美甲，穿戴甲具备三个决定性优势：

| 特性 | 说明 |
| --- | --- |
| 即贴即用 | 无需预约、无需等待，随时佩戴 |
| 可重复佩戴 | 一副可多次使用，单次成本被摊薄 |
| 不伤本甲 | 不打磨、不照灯，对指甲零损伤 |

这三个特性共同指向一个结果：**穿戴甲的消费频次远高于传统美甲**，而频次一高，"款式个性化"就从加分项变成了刚需。

### 1.2 行业痛点

穿戴甲的定制环节仍停留在**社交软件沟通**的原始状态，由此产生三个连锁问题：

**痛点一：需求表达失真。** 顾客想要"奶杏色、方圆甲、无名指带一朵白色小花"，只能靠文字描述，甚至要发一堆参考图来回确认。颜色、甲型、图案在语言里本就是模糊的。

**痛点二：成品与预期不符，反复返工。** 商家依据文字描述打样，做出来的东西和顾客脑子里的画面常常不是一回事。返工意味着双方时间成本翻倍，还可能直接导致差评与退单。

**痛点三：履约过程不可追踪。** 订单在微信里，接单没接单、做到哪一步了、什么时候能取，全靠人工回复。商家的经营数据也没有沉淀，无法知道哪些款式好卖。

### 1.3 本项目要解决的问题

一句话概括：**把"靠嘴描述"变成"所见即所得"，把"口头订单"变成"结构化订单"。**

具体拆成三个必须解决的技术问题：

| 问题 | 本项目给出的解法 |
| --- | --- |
| 顾客怎么表达清楚想要什么？ | **可视化设计台**：真实手模上五指独立设计，实时预览 |
| 商家怎么保证做出来和设计的一致？ | **设计快照**：设计序列化为不可变 JSON 参数 + 预览图，订单项只引用快照，商家按快照 1:1 制作 |
| 履约过程怎么管？ | **订单状态机 + 双履约模式**：状态全程可追踪，到店自提（自提码核销）或商家邮寄 |

### 1.4 研究意义

**工程意义**：本项目没有采用"素材图拼贴"的常规做法，而是自研了**参数化渲染引擎** —— 甲型、款式、效果层、钻饰全部由代码按参数实时生成 SVG。这意味着：
- 甲型与长度彻底解耦（8 种甲型 × N 种长度，不需要 8×N 张图）；
- 效果层可任意叠加组合（20 种效果层多选叠加，而非单选互斥）；
- 素材到位后可无缝替换为 PNG，业务数据结构不变。

**产品意义**：为"非标定制品电商"提供了一个可复用的解法 —— **快照化**。定制品的一切纠纷都源于"设计态"与"生产态"的信息差，而快照把设计态在时间轴上冻结，从机制上消除了这个信息差。

**教学意义**：完整覆盖了软件工程的主要环节 —— 需求分析（用例图/时序图/ER 图）、系统设计（分层架构/数据库设计）、编码实现、单元测试（8 个测试类，覆盖状态机全流转、并发、上传安全）、部署交付。

## 二、产品定位与目标用户

### 2.1 产品定位

**面向 C 端的穿戴甲在线定制与交易平台**，同时为商家提供 B 端履约与经营后台。

- 商品形态：按副定制的非标品，参考单价 ￥39/副
- 核心差异：**所见即所得的可视化定制**
- 履约方式：到店自提 / 商家邮寄

### 2.2 目标用户

| 角色 | 画像 | 核心诉求 |
| --- | --- | --- |
| **顾客** | 18–35 岁女性，追求个性但缺乏绘画/美甲专业知识 | 能直观设计、能确认成品、能追踪进度 |
| **商家** | 中小美甲店主或穿戴甲手作商家 | 降低沟通成本、按图制作不返工、经营数据可看 |
| **管理员** | 平台运营方 | 治理违规账号、掌握平台整体数据 |

### 2.3 角色权限模型

三级角色，前端路由与后端接口**双向**鉴权：

| 角色 | 值 | 权限范围 |
| --- | --- | --- |
| 顾客 | `USER` | 浏览、设计、下单、评价、个人中心 |
| 商家 | `MERCHANT` | 顾客权限 + `/api/merchant/**`（看板/素材/模板/订单/评价/公告/门店/统计） |
| 管理员 | `ADMIN` | 商家权限 + `/api/admin/**`（平台看板/用户管理） |

## 三、核心设计决策（为什么这样设计）

这一节回答"为什么" —— 是答辩时最容易被追问的部分。

### 决策一：为什么设计台用「参数化渲染」而不是「素材图拼贴」

**常规做法**：把甲型、图案、效果都做成切好的 PNG，用户选择时叠加图片。

**这个做法的问题**：
1. 甲型 × 长度 × 图案 × 效果层的组合是**乘法级**的素材量，美术成本不可控；
2. 图片是死的，无法按长度伸缩 —— 短甲和长甲得各切一套图；
3. 效果层只能单选，因为两张不透明 PNG 叠加会互相遮挡。

**本项目的做法**：全部由代码按参数实时生成 SVG。

| 模块 | 职责 | 关键设计 |
| --- | --- | --- |
| `contours.js` | 8 种甲型轮廓 | 甲型 = 参数化 SVG path，**长度是独立系数 k∈[0.6,2.8]**，同一函数按 k 生成不同长度轮廓 |
| `patternStyles.js` | 10 种参数化款式 | 元信息 + 纯函数生成器 + `paramsSchema` 驱动参数面板 |
| `polishOverlays.js` | 20 种效果覆盖层 | GLOSS/PEARL/SHIMMER/EFFECT/SPECIAL 五类，**全部半透明、可多选叠加** |
| `decoGems.js` | 钻饰水晶 | 底色 → 冠部切面 → 彩虹折射 → 内缘暗部 → 外缘亮边 → 定点高光，六层合成 |

**关键收益**：
- **甲型与长度解耦**：`杏仁形` 只有一条 path 定义，短/中/长/超长都由长度系数推导 —— 这直接对应了产品上的一个明确要求（"短杏仁形、长杏仁形都应属于同一种杏仁形"）；
- **效果层可叠加**：珠光 + 细闪 + 极光能同时存在，因为每一层都是半透明 SVG 元素；
- **可复现**：所有随机元素用 `seededRandom(seed)` 生成，**同一设计每次渲染结果完全一致**，不会"刷新一次变个样"。

**并且预留了演进路径**：「**参数化渲染 + 后续 PNG 无缝替换**」双通道 —— 素材的 `image_url` 为空则走代码渲染，有值则叠加透明 PNG，**业务数据结构完全不变**。这样一期能用代码跑通全部链路验证效果，二期美术素材到位后只换素材源。

### 决策二：为什么设计必须「快照化」才能进入交易

这是**定制商品区别于普通电商的根本机制**。

**问题**：素材库是活的 —— 商家随时可能改色卡、下架贴花。如果订单只存"设计 id"，那么商家三个月后打开这个订单，按当前素材库渲染出来的甲，可能和顾客当初设计的**不是同一副**。

**解法**：
```
保存设计 = 序列化五指全量参数（JSON params）
         + 渲染预览图（html2canvas 截图上传）
         ↓
购物车 / 订单项只引用这个不可变快照
（order_item.designParams / designName / previewUrl / price / quantity）
```

**收益**：
- 商家后续改素材库，**不影响已下单的生产依据**；
- 订单详情 = 预览大图 + 参数清单，用户能确认"我买的就是我设计的"；
- 模板（`template.design_params`）与用户设计（`design.params`）**共用同一份数据结构**，一键套用无需格式转换。

### 决策三：为什么设计台出口要「完成即转化」

穿戴甲是低价非标品（￥39/副），用户在设计台点下"保存"的那一刻，**购买意图最成熟**。从"保存"到"购买"之间每多跳一个页面，转化就掉一截。

因此设计台的出口不是"跳转到我的设计列表"，而是弹出三选一浮层：

- **继续编辑**（留在设计台）
- **保存并加入购物车**
- **保存并立即结算**

未登录时点保存 → 跳登录并携带 `redirect`，登录后回到设计台继续。

### 决策四：为什么采用「双履约模式」

穿戴甲的交付有真实的场景分化：

| 模式 | 适用场景 | 关键机制 |
| --- | --- | --- |
| **到店自提** | 同城、顾客愿意到店 | 免运费；制作完成生成 **6 位全局唯一自提码**，到店凭码核销 |
| **商家邮寄** | 异地 | 固定运费 ￥8，满 ￥99 包邮；发货时录入快递公司与单号 |

运费规则的**权威配置在后端** `application.yml`（`nail.freight.amount` / `free-over`），前端仅作展示 —— 避免前后端各写一份规则导致金额不一致。

### 决策五：为什么订单流转要收敛到「状态机」

订单状态散落在各个 if-else 里是典型的维护灾难：新增一个状态就要全局搜索所有判断点，漏一处就是脏数据。

本项目把**全系统唯一的流转规则表**收敛到一个类：

```java
// OrderStateMachine：from -> 允许的 to 集合（终态无出边）
PENDING_PAY → {PAID, CANCELLED}
PAID        → {PRODUCING, CANCELLED}
PRODUCING   → {WAIT_PICKUP, WAIT_SHIP}
WAIT_PICKUP → {VERIFIED}
WAIT_SHIP   → {SHIPPED}
SHIPPED     → {RECEIVED}
```

所有状态变更必须经过 `assertTransition(from, to)` 校验，非法流转（含未知/空状态等脏数据）统一拦截。每次变更写 `order_status_log`，形成完整时间线。

### 决策六：为什么 UGC 素材要走「私有目录 + 审核流」

顾客可以上传自定义贴纸（透明底 PNG）。如果直接存到公开的 `uploads/` 目录，那么**未审核的内容就能被任何人通过 URL 访问** —— 这是内容安全的漏洞。

因此：
- 待审素材存 `private-uploads/`，**不映射为静态资源**；
- 读取统一走 `GET /api/materials/{id}/image` 接口鉴权；
- 可见性规则：审核通过 → 全员可见；待审 → 仅上传者本人 + 运营角色可见；驳回 → 对上传者隐藏。

## 五、业务规则

### 5.1 订单状态机

```
待付款 ──支付──> 待接单 ──接单──> 制作中 ──┬──自提──> 待自提 ──核销──> 已核销（终态）
   │                  │                    └──邮寄──> 待发货 ──发货──> 已发货 ──收货──> 已签收（终态）
   └──取消──> 已取消（终态）
```

- 终态：已核销 / 已签收 / 已取消，**无出边**
- 每次变更写 `order_status_log`（含操作人、备注）
- 自提码：制作完成时生成 6 位数字，**全局唯一**，核销时校验

### 5.2 运费规则

| 条件 | 运费 |
| --- | --- |
| 到店自提 | ￥0 |
| 邮寄且商品金额 < ￥99 | ￥8 |
| 邮寄且商品金额 ≥ ￥99 | ￥0（含等于，边界有单测覆盖） |

### 5.3 素材审核规则

| 审核状态 | 顾客可见性 | 商家可见性 |
| --- | --- | --- |
| `PENDING` 待审 | 仅上传者本人 | 可见（可审核） |
| `APPROVED` 通过 | 全员 | 可见 |
| `REJECTED` 驳回 | 不可见 | 可见 |

### 5.4 售后规则

**状态流转**

```
PENDING（顾客提交，待商家处理）
  ├─ 商家同意 → COMPLETED（已退款，终态）
  └─ 商家拒绝 → REJECTED（终态）
```

| 规则 | 说明 |
| --- | --- |
| 可申请范围 | 仅「已签收 / 已核销」的订单（未完成的订单走取消流程） |
| 一单一售后 | 已提交过申请（无论结果）不可重复提交，避免反复骚扰 |
| 退款金额 | **由后端按订单实付金额计算**，不接受前端传值，防止伪造金额 |
| 凭证图 | 最多 3 张，规则同晒图（jpg/png/webp ≤5MB） |
| 拒绝原因 | 拒绝时必填，≤200 字，会推送给顾客 |
| 并发防护 | 处理时条件更新（仅 PENDING 可被处理），防止两个审核请求互相覆盖 |

### 5.5 消息通知规则

| 触发节点 | 接收方 | 内容 |
| --- | --- | --- |
| 订单支付成功 | 商家 | 有新订单待接单 |
| 商家接单 | 顾客 | 订单已接单，制作中 |
| 制作完成 | 顾客 | 自提：附自提码；邮寄：待发货 |
| 商家发货 | 顾客 | 快递公司 + 单号 |
| 自提核销 | 顾客 | 订单已完成 |
| 确认收货 | 商家 | 顾客已签收 |
| 订单取消（双方） | 对方 | 订单被取消 |
| 提交售后申请 | 商家 | 新的售后申请（含金额） |
| 售后审核结果 | 顾客 | 已通过（含退款金额）/ 被拒绝（含原因） |

- 采用「登录后拉取 + 未读红点」方案，不做 WebSocket 实时推送（成本低、对现有架构零侵入）
- 通知写入失败**不影响主业务**（内部捕获异常，避免主事务回滚）
- 打开通知面板即标记全部已读

### 5.6 其他约束

- 收货地址最多 10 条
- 购物车单项数量有上限（超限拒绝，含并发累加场景）
- 素材被设计引用时禁止删除，只能下架
- 同类型下素材 `code` 唯一
- 色卡必须符合 `#RRGGBB` 格式
- 甲型 / 参数化款式的 `code` 必须绑定前端渲染器（不能凭空发明）

## 六、非功能性需求

| 维度 | 落实方式 |
| --- | --- |
| **可靠性** | 关键操作 `@Transactional(rollbackFor)`；核心表逻辑删除 `@TableLogic`；订单全链路状态日志 |
| **安全性** | Spring Security + JWT；BCrypt 密码；三角色分级鉴权；上传三重校验（路径穿越 / 伪装图片 / 透明通道）；JWT 弱密钥拒绝启动 |
| **可用性** | 撤销重做、拖拽投放、表单防御性校验、统一中文错误提示 |
| **可维护性** | Controller–Service–Mapper 分层；统一 `Result` / `PageResult` 封装 + 全局异常处理 |
| **可扩展性** | `material.type + code` 作为品类扩展点，新增美甲品类无需改表结构 |
| **可测试性** | 8 个测试类覆盖状态机全流转、运费边界、并发、上传安全、JWT 校验 |

## 八、边界与非目标（明确不做什么）

明确划出边界，避免范围膨胀：

| 项 | 状态 | 理由 |
| --- | --- | --- |
| 真实支付对接 | **不做** | 模拟支付已满足演示；`POST /orders/{id}/pay` 预留了沙箱接入点 |
| 甲片尺寸分码 | **不做** | 当前均码 + 订单备注可覆盖需求 |
| 分享海报 / 小程序码 | **不做** | 列为 P2 迭代 |
| 钻饰模块（JEWEL） | **暂时下线** | 引擎已就绪，按需恢复接线 |
| 素材漂移兜底 | **接受** | 素材库变更后旧设计按当前素材渲染会有细微差异，已通过订单快照（含预览图）缓解 |
