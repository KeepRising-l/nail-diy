## 一、开场陈述（3 分钟版，可直接背）

**各位老师好，我汇报的题目是《基于 Spring Boot 的 DIY 穿戴甲定制平台》。**

**（1）为什么做这个题目 —— 30 秒**

穿戴甲是美甲品类里增长最快的细分市场，它的特点是即贴即用、可重复佩戴、不伤本甲。但它的**定制环节还停留在社交软件沟通的原始状态**：顾客只能靠文字描述想要什么，商家依据文字打样，成品与预期不符、反复返工的情况非常普遍；同时订单进度全靠人工回复，商家的经营数据也没有沉淀。

**这个项目要解决的核心问题就一句话：把"靠嘴描述"变成"所见即所得"，把"口头订单"变成"结构化订单"。**

**（2）做了什么 —— 60 秒**

系统采用前后端分离架构，包含三个端：

- **顾客端**：核心是**可视化设计台**。顾客在真实手模上五指独立设计，实时预览甲型、长度、色号、渐变、猫眼、法式、波点、贴花和效果层，所见即所得。
- **商家端**：数据看板、素材与模板管理、订单履约（接单→制作→发货 / 自提码核销）、评价与公告管理、门店管理、销售统计。
- **管理端**：平台数据看板与用户治理。

技术栈是 Spring Boot 3.3 + Vue 3 + MySQL 8，JWT 做无状态认证，三级角色分级鉴权。

**（3）技术亮点 —— 90 秒（重点讲前两个）**

**第一个亮点是自研的参数化渲染引擎。** 常规做法是把甲型、图案都做成切好的图片来拼贴，但那样素材量是乘法级的，而且甲型没法随长度伸缩。我们改成**全部由代码按参数实时生成 SVG**：
- 8 种甲型是 8 条参数化路径，**长度是一个独立系数**，所以"短杏仁形"和"长杏仁形"是同一种甲型的两个长度，而不是两张图；
- 20 种效果层全部是半透明图层，**可以任意叠加组合**，珠光加细闪加极光能同时存在；
- 而且预留了演进通道：素材的图片地址为空时走代码渲染，有值时就叠加透明 PNG，**业务数据结构完全不变**。

**第二个亮点是手模的逐指嵌入几何。** 常规做法是把一个椭圆贴在手指上，看起来就是贴纸。我们的做法是：从手图上**逐指实测**锚点坐标、甲床宽度、甲床长度、指轴夹角和肤色，让甲片根部锚定在甲缘线上、绕甲根旋转、长度只向指尖延伸，再用一层肤色新月遮罩盖住甲片根部 —— 产生"从皮肤里长出来"的嵌入感。

**第三个亮点是设计快照机制。** 设计会序列化成五指全量参数加预览图，订单项只引用这个不可变快照。这样商家后续改素材库，**不影响已经下单的生产依据**，从机制上消除了定制品"设计与生产不一致"的纠纷。

**（4）质量保障 —— 30 秒**

写了 8 个测试类，测试点不是凑数，而是打在真正的风险上：订单状态机的全流转表用参数化测试遍历、运费包邮门槛的边界值、购物车并发插入、文件上传的路径穿越和伪装图片校验、JWT 的弱密钥和过期校验。

**（5）不足与展望 —— 30 秒**

目前的不足主要有三块：一是支付是模拟实现，真实支付需要接沙箱；二是素材库变更后，旧设计按当前素材渲染会有细微差异，我们已经通过订单快照的预览图做了缓解；三是部分体验细节还在打磨，比如灵感库对游客的开放、结算后的支付引导。后续会优先补上这些。

**我的汇报完毕，请各位老师批评指正。**

## 三、高频问题 Q&A

### A 类：项目背景与需求

**Q1：为什么选择穿戴甲这个方向？**
穿戴甲是美甲品类里增长最快的细分市场，它即贴即用、可重复佩戴、不伤本甲，所以**消费频次远高于传统美甲**。频次一高，个性化就从加分项变成刚需。但它的定制环节还停留在社交软件沟通，这是真实存在的痛点。

**Q2：这个项目解决的核心问题是什么？**
两个：**需求表达失真**（顾客只能靠文字描述，颜色甲型图案在语言里本就是模糊的）和**履约不可追踪**（订单在微信里，进度全靠人工回复，经营数据无沉淀）。解法是"所见即所得的可视化定制"+"结构化订单"。

**Q3：目标用户是谁？**
顾客是 18–35 岁、追求个性但缺乏美甲专业知识的女性；商家是中小美甲店主或穿戴甲手作商家；还有平台运营方作为管理员。

**Q4：为什么定价是 ￥39？**
穿戴甲是按副定制的非标品，单价低、决策成本低，这个价位符合当前市场主流的穿戴甲定价区间。低单价也意味着**转化路径必须极短**，这直接影响了我后面的一个设计决策（"完成即转化"）。

### B 类：技术选型

**Q5：为什么用 Spring Boot 3.3 而不是 2.x？**
Spring Boot 3.x 要求 Java 17，我们用的是 JDK 17。3.x 的 Spring Security 6 在授权配置上用了 Lambda DSL，比 2.x 更清晰；另外 3.x 对 Jakarta EE 9+ 的支持是原生的。

**Q6：为什么用 JWT 而不是 Session？**
前后端分离 + 多端（顾客端/商家端/管理端），JWT 是**无状态**的，服务端不用存会话，水平扩展时不用考虑会话共享。代价是令牌无法主动失效，我们通过较短的有效期（默认 7 天）和账号状态校验来缓解 —— 过滤器里每次都会查一次用户状态，**被禁用的账号即使持有有效令牌也无法访问**。

**Q7：为什么用 MyBatis-Plus 而不是 JPA？**
项目里的统计功能有大量聚合查询（销售趋势、履约占比、设计偏好 TOP5），MyBatis-Plus 允许直接用 `@Select` 写原生 SQL，比 JPA 的 Criteria API 或 JPQL 更直接可控。同时 MyBatis-Plus 提供的 `@TableLogic` 逻辑删除、分页插件又省掉了大量样板代码。

**Q8：为什么前端选 Vue 3 而不是 React？**
Vue 3 的 Composition API 更适合把渲染引擎这类**纯函数逻辑**和组件解耦（我们的四个引擎模块就是独立于组件的纯 JS）；另外 Element Plus 提供了完整的后台管理组件，商家端和管理端能快速搭建。

**Q9：为什么手模用位图而不是纯 SVG 画一只手？**
纯 SVG 画的手很难做到真实肤质和光影。我们的做法是**位图手模 + SVG 甲片**混合：手部用透明底位图保证真实感，甲片用 SVG 保证可参数化编辑。代价是需要逐指实测锚点，但这部分是一次性的。

### C 类：核心难点（最容易被深挖）

**Q10：设计台的甲型为什么能做到"短杏仁形和长杏仁形是同一种甲型"？**
因为**甲型只定义轮廓的形状函数，长度是独立的系数**。`contours.js` 里每个甲型是一个接收长度系数 k 的函数，返回一条 SVG 路径。k 从 0.6 到 2.8，同一函数按不同的 k 生成不同长度的轮廓，根部位置和宽度不变，只有尖端延伸。

**Q11：效果层为什么能叠加？图片叠加不是会互相遮挡吗？**
关键在于**效果层全部是半透明的 SVG 元素**，而不是不透明的图片。比如珠光是用细小的半透明圆形颗粒铺出来的，细闪也是，所以两层叠加时下层不会被遮住。数据结构上，`overlays` 是一个数组 `[{id, opacity}]`，而不是单个 id，所以天然支持多选。

**Q12：为什么同一个设计每次渲染结果都一样？**
因为我们用了**种子随机**（`seededRandom`）。所有需要随机的地方（波点位置、闪粉分布）都用固定的种子生成，种子由手指索引和参数推导出来，所以同一个设计每次渲染完全一致。如果用 `Math.random()`，用户刷新一次波点位置就全变了。

**Q13：手模上的甲片怎么保证"不像贴纸"？**
三个机制：
1. **根部锚定**：甲片根缘中心不是放在手指最顶端，而是反推锚点后落在天然甲缘线上；
2. **绕甲根旋转 + 长度只向指尖延伸**：旋转中心设在甲根（`transform-origin: 50% 0`），长度变化时根部不动，只有尖端延伸；
3. **甲缘遮罩**：一层肤色新月盖在甲片根部之上，配合高斯模糊，产生"从皮肤里长出来"的感觉。

**Q14：为什么设计要"快照化"？直接存设计 id 不行吗？**
不行。因为**素材库是活的** —— 商家随时可能改色卡、下架贴花。如果订单只存设计 id，那么三个月后商家打开订单，按当前素材库渲染出来的甲，可能和顾客当初设计的不是同一副。快照把设计态冻结在时间轴上，从机制上消除了这个信息差。

**Q15：为什么把订单状态收敛到一个状态机类？**
因为订单状态散落在各个 if-else 里是典型的维护灾难：新增一个状态就要全局搜索所有判断点，漏一处就产生脏数据。我们把全系统唯一的流转规则收敛成一张 `Map<from, Set<to>>` 规则表，所有状态变更必须经过 `assertTransition` 校验，终态没有出边，未知状态一律拦截。而且这张表可以用参数化测试**完整遍历**。

**Q16：自提码怎么保证不重复？**
生成 6 位随机数字，然后查库校验唯一性，重复就重新生成，最多重试若干次，超限则报错让用户重试。6 位数字空间是 100 万，对于中小商家的订单量冲突概率极低。

**Q17：订单状态并发更新会出问题吗？**
会有"陈旧状态覆盖"的风险 —— 比如两个请求同时基于旧状态做变更。我们的处理是：状态变更时**同时校验来源状态**，如果来源状态已经变了，这次更新就不会生效，也**不会写一条误导性的日志**。这一点有专门的并发测试覆盖。

### D 类：安全与测试

**Q18：上传功能做了哪些安全防护？**
三重校验：
1. **路径穿越**：对上传路径逐段校验，拒绝 `.`、`..` 和非法字符；
2. **伪装图片**：既校验文件头魔数，又用 `ImageIO` 真实解码，扩展名必须与实际内容一致；
3. **透明通道**：贴纸要求必须是含透明像素的 PNG，逐像素扫描校验。
另外还有尺寸限制（≤4096×4096）和文件大小限制（≤5MB）。

**Q19：UGC 用户上传的贴纸怎么防止未审核内容被看到？**
待审核的贴纸存在 `private-uploads/` 目录，**这个目录不映射为静态资源**，所以无法通过 URL 直接访问。读取统一走接口，接口里做鉴权：审核通过的公开可见，待审核的只有上传者本人和运营角色可见，其他情况返回 404（不暴露内容是否存在）。

**Q20：JWT 的密钥怎么管理？**
密钥必须通过环境变量注入，代码里没有默认值。而且启动时会校验密钥长度，**少于 32 位直接拒绝启动**，防止开发环境用了弱密钥带到生产。配置文件里也不会有真实密钥。

**Q21：测试写了哪些？为什么这么选？**
8 个测试类，测试点都打在真正的风险上：
- **订单状态机**：用参数化测试遍历全流转表（合法流转、终态封口、非法跳转、未知状态）
- **运费规则**：包邮门槛的边界值，特别是"恰好等于 99 元"这个含等号的边界
- **并发**：陈旧状态更新不写误导日志、结算只删除锁定的购物车快照
- **文件上传**：路径穿越、伪装图片、透明通道、尺寸限制、私有目录
- **JWT**：过期、签名错误、弱密钥、畸形 claim

### E 类：不足与改进

**Q22：项目有哪些不足？**
两个主要方面：
1. **支付是模拟的** —— `POST /orders/{id}/pay` 直接置为已支付，真实支付需要接沙箱；
2. **素材漂移** —— 素材库变更后，旧设计按当前素材渲染会有细微差异，我们通过订单快照里的预览图做了缓解。

另外，在最终自测阶段发现并修复了 10 项问题（含 1 个影响素材图读取与上传落盘位置的文件路径缺陷、时间格式、灵感库对游客开放、结算后支付引导等），清单见《链路验证与问题清单》。

**Q23：如果继续做，下一步做什么？**
业务闭环已经补齐：体验层做了灵感库对游客开放、结算后自动引导支付、运费配置接口化、创建接口返回 id；
业务层补上了**售后/退款流程**与**消息通知**。
下一步按优先级是：真实支付对接 → 甲片尺寸分码 → 分享海报 / 小程序码 → 钻饰模块恢复上线。

**Q24：这个项目最大的技术难点是什么？**
**手模的逐指嵌入几何**。因为它没有现成方案，需要从手图上逐指实测锚点、宽度、长度、角度，再推导出一套长度映射函数，还要处理拇指这种大斜角的特殊情况。中间反复调整了很多轮，最终靠"根部锚定 + 只向指尖延伸 + 甲缘遮罩"三个机制配合才达到效果。

## 四、刁钻问题预案

**Q：你的渲染引擎是自己写的，还是用了现成的库？**
是自己写的。四个模块（`contours` / `patternStyles` / `polishOverlays` / `decoGems`）都是纯 JS 函数，输入参数输出 SVG 元素描述数组，不依赖任何图形库。这也是为什么它能和 Vue 组件解耦 —— 它们不知道 Vue 的存在。

**Q：效果层的"可叠加"听起来很普通，技术上到底难在哪？**
难在**叠加后不能互相遮挡，也不能失真**。如果效果层是不透明图片，两层叠加下层就看不见了。所以每一层必须设计成半透明的、独立的视觉元素 —— 比如珠光是几十个半透明小圆，细闪也是，它们叠加时是"颗粒叠加颗粒"，视觉上是融合的。另外还要保证所有层都被甲片轮廓正确裁剪，这靠统一的 `clipPath` 实现。

**Q：快照机制会不会导致数据冗余？比如同一个设计下十单，是不是存十份参数？**
会，这是**有意的冗余**。因为快照的意义就是"订单不受后续变更影响"，共享引用就破坏了这个前提。参数是 JSON，一副设计的参数大概几百字节到几 KB，相对于它带来的"生产依据不可变"的价值，这个存储成本是完全可以接受的。

**Q：为什么不做甲片尺寸分码？**
因为穿戴甲目前市场上主流还是均码 + 备注（顾客可以在订单备注里写手指尺寸）。分码会让设计台的参数维度再增加一维，复杂度上升但收益有限，所以在当前版本里明确列为非目标。

**Q：如果商家改了素材库，已经下的订单怎么办？**
订单里的设计参数是快照，**完全不受影响**。商家打开订单看到的还是下单时的参数和预览图，按那个制作就行。唯一的差异是：如果商家在**商家端的订单列表**里重新渲染这个设计，由于素材库变了，渲染结果可能有细微差异 —— 所以我们在订单项里同时存了下单时的预览图，以预览图为准。

**Q：系统能支持多少用户？做过压力测试吗？**
没有做正式的压力测试，这是当前版本的局限。架构上做了一些准备：无状态 JWT 便于水平扩展、连接池用 HikariCP、素材表建了 `idx_type_status` 等索引支撑高频查询。但如果要支撑真实业务量，还需要做压测和针对性的优化。

**Q：为什么订单状态是这六个？能不能更少？**
六个状态是**业务必要的最小集**：待付款（支付前）、待接单（已付待商家确认）、制作中（商家已接单）、待自提/待发货（制作完成，按履约方式分流）、已核销/已签收（终态）。不能更少的原因是"制作中"这个状态对顾客体验很重要 —— 顾客需要知道商家已经开始做了，而不是付了钱就石沉大海。
